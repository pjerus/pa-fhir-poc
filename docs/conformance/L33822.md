## Validator flags, and why

- **`-tx n/a`** — no terminology server. Structure and profile constraints are
  fully verified; code-membership is not. The codes here are HCPCS and
  ICD-10-CM, neither freely distributable as FHIR CodeSystem content, so
  terminology checking would be partial at best. Stated rather than implied.
- **`-allow-example-urls`** — instance canonicals are `example.org` by design
  (`src/fhir/profiles.ts` `CANONICAL_BASE`): this repo publishes no FHIR
  endpoint, and a placeholder that *looks* real would be worse. The flag marks
  the placeholder as deliberate; every other check runs normally. A deployment
  that publishes these artifacts would set a real canonical base and drop the
  flag.

## Remaining warnings (all explained, none fixable in scope)

- **31× on PlanDefinition**: `A definition for CodeSystem
  'http://www.cms.gov/Medicare/Coding/HCPCSReleaseCodeSets' could not be
  found` — one per covered HCPCS code. The system URI is correct
  (verified against THO v7.3.0); the validator simply has no HCPCS CodeSystem
  content to resolve codes against, because CMS does not publish HCPCS as a
  FHIR package and it is not freely redistributable. Every `Coding` carries
  the right URI, so a consumer with HCPCS terminology validates these
  normally.

## What the validator run changed

Two genuine conformance gaps surfaced on the first run and were fixed in
`src/fhir/` (generically — no L33822-specific code):

1. `Questionnaire.subjectType` — 1..1 in `dtr-base-questionnaire`; now emitted
   as `["Patient"]`.
2. dom-6 best-practice narrative — both FHIR resources now carry a generated
   `text` narrative.
